# Calendar Module Database Schema

Part of **Roommate OS**. Database: PostgreSQL.

This schema describes custom calendar events only. Chore due dates are read from the separate chores tables when the combined calendar view is built, so they are not copied here. Bill management is not implemented.

This module assumes `users` and `households` tables already exist (members module), each with a `user_id` / `household_id` primary key.

## Tables

### `events`

| Column | Type | Notes |
|---|---|---|
| `event_id` | BIGINT, PK | Auto-generated |
| `household_id` | BIGINT, FK → `households` | Required. Deleting a household deletes its events |
| `created_by` | BIGINT, FK → `users` | Owner of the event |
| `name` | VARCHAR(200) | Required |
| `description` | TEXT | Optional |
| `start_timestamp` | TIMESTAMPTZ | Required |
| `end_timestamp` | TIMESTAMPTZ | Required, must be after start |
| `all_day` | BOOLEAN | Default `false` |
| `recurring` | `recurrence_type` | `NONE`, `DAILY`, `WEEKLY`, `MONTHLY`. Default `NONE` |
| `recurrence_until` | DATE | Optional end date of the series. `NULL` means it repeats indefinitely. Only allowed when `recurring` is not `NONE` |
| `created_at` | TIMESTAMPTZ | Default `now()` |
| `updated_at` | TIMESTAMPTZ | Default `now()` |

### `event_attendees`

Many-to-many mapping between events and household members.

| Column | Type | Notes |
|---|---|---|
| `event_id` | BIGINT, FK → `events` | Part of the composite PK. Cascades on delete |
| `user_id` | BIGINT, FK → `users` | Part of the composite PK. Cascades on delete |

**Rule:** No rows for an event means it involves the whole household. Rows exist only when specific members are chosen. Attendees must belong to the event's household. The application enforces this.

### `event_exceptions`

Stores changes to a single occurrence of a recurring event. One row means "this occurrence is different from what the series rule would generate". The series row in `events` is never touched.

| Column | Type | Notes |
|---|---|---|
| `event_id` | BIGINT, FK → `events` | Part of the composite PK. Cascades on delete |
| `original_start` | TIMESTAMPTZ | Part of the composite PK. Start time of the occurrence as generated by the series, which identifies it |
| `is_cancelled` | BOOLEAN | `true` means this occurrence was deleted. Default `false` |
| `name` | VARCHAR(200) | Optional override |
| `description` | TEXT | Optional override |
| `start_timestamp` | TIMESTAMPTZ | Optional override, e.g. moved to another time |
| `end_timestamp` | TIMESTAMPTZ | Optional override |

**Rules:**
- Deleting one occurrence inserts a row with `is_cancelled = true`.
- Editing one occurrence inserts or updates a row with only the changed fields set. Columns left `NULL` fall back to the series values.
- Attendees can't be changed for a single occurrence in the MVP. They always come from `event_attendees`.

## SQL

```sql
CREATE TYPE recurrence_type AS ENUM ('NONE', 'DAILY', 'WEEKLY', 'MONTHLY');

CREATE TABLE events (
    event_id         BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    household_id     BIGINT NOT NULL REFERENCES households(household_id) ON DELETE CASCADE,
    created_by       BIGINT NOT NULL REFERENCES users(user_id),
    name             VARCHAR(200) NOT NULL,
    description      TEXT,
    start_timestamp  TIMESTAMPTZ NOT NULL,
    end_timestamp    TIMESTAMPTZ NOT NULL,
    all_day          BOOLEAN NOT NULL DEFAULT FALSE,
    recurring        recurrence_type NOT NULL DEFAULT 'NONE',
    recurrence_until DATE,
    created_at       TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at       TIMESTAMPTZ NOT NULL DEFAULT now(),
    CONSTRAINT events_end_after_start CHECK (end_timestamp > start_timestamp),
    CONSTRAINT events_until_needs_recurrence CHECK (recurrence_until IS NULL OR recurring <> 'NONE')
);

CREATE INDEX idx_events_household_start ON events (household_id, start_timestamp);

CREATE TABLE event_attendees (
    event_id BIGINT NOT NULL REFERENCES events(event_id) ON DELETE CASCADE,
    user_id  BIGINT NOT NULL REFERENCES users(user_id) ON DELETE CASCADE,
    PRIMARY KEY (event_id, user_id)
);

CREATE INDEX idx_event_attendees_user ON event_attendees (user_id);

CREATE TABLE event_exceptions (
    event_id        BIGINT NOT NULL REFERENCES events(event_id) ON DELETE CASCADE,
    original_start  TIMESTAMPTZ NOT NULL,
    is_cancelled    BOOLEAN NOT NULL DEFAULT FALSE,
    name            VARCHAR(200),
    description     TEXT,
    start_timestamp TIMESTAMPTZ,
    end_timestamp   TIMESTAMPTZ,
    PRIMARY KEY (event_id, original_start),
    CONSTRAINT exceptions_end_after_start
        CHECK (start_timestamp IS NULL OR end_timestamp IS NULL OR end_timestamp > start_timestamp)
);
```

## Reading events for a date range

For a range `[from, to]` in a household, fetch rows where:

- `start_timestamp <= to`, and
- either `recurring = 'NONE'` and `end_timestamp >= from`, or `recurring <> 'NONE'` and (`recurrence_until IS NULL` or `recurrence_until >= from::date`).

The application then expands recurring rows into occurrences inside the range. Occurrences are not stored. For each occurrence, look up `event_exceptions` by `(event_id, original_start)`:

- If a row exists with `is_cancelled = true`, skip the occurrence.
- If a row exists with overrides, use its non-`NULL` fields in place of the series values.
- Otherwise use the series values.

Fetch the exceptions for all returned events in one query rather than one per occurrence.

## Limitations (MVP)

- "This and all following occurrences" is not supported. A change applies either to one occurrence or to the whole series.
- Attendees can't differ per occurrence.
- No RSVP status. Adding an `status` column to `event_attendees` is the path to invites later.
- No link to external calendars (Google/Apple).
